Ce que ce rapport couvre

L'architecture applicative et infrastructure (Blue-Green), le pipeline CI/CD et ses contrôles de sécurité, le dispositif de monitoring/alerting mis en place, la procédure de gestion d'incident et de rollback, le post-mortem de l'incident P1 d'août 2024 qui a motivé l'essentiel de ces travaux, ainsi que les points opérationnels traités récemment et les recommandations restantes.

Architecture technique

Vue applicative (microservices) et vue infrastructure (Blue-Green EC2/k3s).

Vue applicative

Frontend React consommé via un API Gateway (Node.js/Express), routant vers quatre microservices métier partageant une base PostgreSQL et un cache Redis.

Frontend → API Gateway → microservices (Auth, Paie, Congés, Recrutement) → PostgreSQL / Redis
Composant Rôle
Service Auth JWT (access + refresh), stateless — aucune session serveur à répliquer entre couleurs lors d'une bascule
Paie / Congés / Recrutement Logique métier, périmètre de données propre dans PostgreSQL
PostgreSQL (RDS) Base relationnelle partagée par tous les services et les deux couleurs
Redis Cache applicatif, déployé par couleur

Infrastructure — stratégie Blue-Green

Deux instances EC2 indépendantes (Ubuntu 24.04 ARM64 + k3s), une par couleur, dans des zones de disponibilité différentes. Une seule sert le trafic public (active), l'autre reçoit le prochain déploiement (idle).

Ressource Détail
Application Load Balancer Une target group par couleur ; le listener pointe vers la couleur active. URL stable, jamais de changement visible côté utilisateur
RDS PostgreSQL (db.t4g.micro, 20 Go) Partagée entre les deux couleurs → discipline de migration additive-only obligatoire
Pourquoi Blue-Green

Le déploiement ne touche jamais la couleur qui sert le trafic : nouvelle version déployée + smoke-testée sur l'idle, puis bascule atomique du listener ALB — aucune reconstruction, pas de downtime. Rollback = rebascule vers l'ancienne couleur, toujours active.

Réseau & accès

  • Chaque EC2 n'accepte le port 80 que depuis l'ALB (security group) — jamais exposée directement
  • RDS jamais publique — accessible uniquement depuis les EC2 k3s (blue + green)
  • Accès CI aux instances exclusivement via AWS Systems Manager (SSM), pas de SSH exposé
  • HTTPS pas encore configuré (pas de domaine + certificat ACM à ce stade) — trafic servi en HTTP

Monitoring & alerting

CloudWatch → SNS → email, sans PagerDuty à ce stade.

11 alarmes

Gestion des incidents & rollback

Classification de sévérité et procédure de bascule Blue-Green.

Classification de sévérité

Sévérité Définition Exemples
P1 — Critique Trafic public impacté, ou risque imminent de coupure totale EC2 down / ALB unhealthy sur la couleur active, ALB 5xx élevé, RDS storage bas
P2 — Majeur Dégradation de service, sans coupure CPU EC2/RDS élevé soutenu, latence ALB élevée
P3 — Mineur Aucun impact utilisateur Toute alarme sur la couleur idle

La couleur concernée (active vs idle) change la sévérité réelle d'une alarme identique — première chose à vérifier (terraform output -raw active_color).

Rollback Blue-Green

rollback.yml (déclenchement manuel) rebascule le listener ALB vers la couleur non active, qui tourne déjà la dernière version connue-bonne. Aucun redéploiement — juste un changement de cible ALB, effectif en quelques secondes.

Limite importante

La RDS est partagée entre les deux couleurs : un rollback ALB ne résout rien pour un incident d'origine RDS (espace disque, CPU, mémoire) — il faut traiter la base directement.

Procédure détaillée pas-à-pas : docs/RUNBOOK-INCIDENT.md.

Points opérationnels traités récemment

Un sujet concret résolu pendant la mise en place de ce dispositif.

Tag ECR immuable et pushes concurrents

Le repository ECR est configuré en image-tag-mutability=IMMUTABLE. Le pattern de travail (branche dev-* fast-forwardée vers main, sans commit de merge) fait que le pipeline se déclenche deux fois pour le même commit SHA — le second push Docker échoue alors car le tag existe déjà.

Contournement / amélioration identifiée

Un nouveau commit change le SHA et débloque immédiatement. Amélioration durable identifiée : vérifier l'existence du tag avant build/push dans docker.yml et skip proprement si déjà présent.

Recommandations & prochaines étapes

Ce qui reste à traiter pour consolider le dispositif actuel.

  1. Déployer les nouvelles alarmes (CPU, ALB, RDS) en production — seule ec2-down y est active pour l'instant
  2. Rendre le job docker idempotent (vérifier l'existence du tag ECR avant build/push)
  3. Activer le blocage strict Trivy (exit-code: 1) une fois la première liste de CVE triée
  4. Formaliser/vérifier la politique de sauvegarde RDS (rétention actuelle : 3 jours) au regard du RPO attendu
  5. Mettre en place HTTPS (nom de domaine + certificat ACM)
  6. Réévaluer PagerDuty si l'astreinte doit devenir formelle au-delà d'une notification email
